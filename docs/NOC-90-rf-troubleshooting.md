# NOC-90: evidence-based RF troubleshooting

Stacks on draft NOC-89 PR #93, commit `1258347a8e24a007620270bb10a4f431bb382c98` (CI #446 passed), retaining NOC-83 through NOC-89 dependencies. No upstream merge or closure is part of this milestone. Existing release-install, backup/restore, isolation and simulation-only requirements remain applicable.

## Operation and evidence

Open **RF Troubleshooting**, select a device and explicitly evaluate stored evidence. This operation writes recommendation/workflow records only. It never invokes collectors, equipment commands, projection, incident reconciliation or remediation. Existing analytics projection must be run independently under its NOC-89 controls. Empty or stale projection is diagnostic data-quality evidence, never proof of a radio failure.

The deterministic catalog supports Ubiquiti/Cambium radio patterns, Racom/Aviat carrier diagnostics, and relevant stored MikroTik resource/interface-delta/OSPF information. It reuses NOC-87–89 validated adapters, historical baselines, consecutive evidence and hysteresis. Noise/SNR patterns support **suspected** interference. Congestion requires measured throughput, capacity/utilization and stable RF evidence; utilization alone is insufficient. Single-carrier loss is distinct from an all-observed-carriers outage. Ethernet alarms remain distinct from RF impairment. Fresh radio-up and TCP-down evidence is explicitly conflicting. Upstream correlation uses fresh independent TCP/synthetic checks and inventory descendants; shared monitoring or power failure remains an alternative.

Each recommendation includes opaque source table/row identifiers, timestamps, normalized facts, bounded historical source references and baseline statistics, unconfirmed hypotheses, safe checks, missing evidence, inventory/link/site references and linked existing incidents. RF Analytics provides historical charts; the troubleshooting detail includes inspectable historical comparisons. Raw payloads, names, IP addresses, credentials, free-form device metadata and technician notes are excluded from AI input. The UI renders notes as React text, never HTML.

Hardware/resource observations are provisional: temperature warnings default to 80 °C (5 °C clear margin), configurable with `RF_TROUBLESHOOTING_TEMPERATURE_WARNING_C`; MikroTik CPU/RAM >90% and positive validated interface-error deltas prompt investigation, not a model-specific hardware-failure conclusion. These single stored observations are explicitly low-confidence and require independent/consecutive confirmation. Model-engineered limits and firmware semantics require separate validation.

## Priority and workflow

Priority is transparent: severity ×15, observed episode duration (one point/30 minutes, capped 10), recurrence (2 per recurrence, capped 10), potential inventory descendants (capped 15), evidence support (0/5/10), and linked active incident (5); total capped 100. Urgent ≥75, high ≥50, otherwise normal. Duration starts at evaluation, not an asserted physical fault start. Descendants are **devices, not customers**. Redundancy is unknown: parallel inventory links alone do not establish working failover and do not reduce urgency. No invented redundancy/customer estimate is used.

A stable device/scope/rule key deduplicates a continuing episode, including dismissed or operator-closed recommendations. Only explicit corroborated health for the relevant scope/rule records recovery; absence, stale readings, missing temperature or conflicting evidence cannot establish it. A subsequent recurrence after confirmed recovery increments the episode and reopens for review. Operator status and evidence state are independent; evidence recovery does not automatically resolve/close records. Closed/dismissed items remain visible via filters. Changed/missing evidence becomes unknown while the last evidence snapshot is retained and labelled with its original timestamps.

Operators/admins can review, acknowledge, investigate, dismiss, add notes, document resolution and close. Resolution text is required before resolution/closure. Notes and audit entries retain episode/user/timestamps; the detail returns the latest 100 of each with a truncation marker. A manually resolved recommendation can return to investigation. All evaluation and workflow writes are audited. Obvious secret assignments/private keys are rejected in notes; operators must still avoid any sensitive text.

## Optional local explanation provider

Normal operation requires no AI. `RF_EXPLANATION_PROVIDER=disabled` is the default. The only optional provider is `local_ollama`, requiring `RF_EXPLANATION_ADMIN_APPROVED=true`; offline mode rejects activation. `RF_EXPLANATION_MODEL=local-rf` selects a pre-provisioned local model. It does not download or launch models. No external AI integration exists. Endpoint is fixed to `http://127.0.0.1:11434/api/generate` in the backend's network namespace. No endpoint override, proxy inheritance or redirects are accepted. Runtime Compose egress isolation is unchanged; a separate reviewed deployment design is needed to host a model in that namespace. Do not enable AI for isolated release acceptance.

The provider gets allowlisted numeric/enum facts and opaque references plus approved check IDs, never device names/IPs/raw metadata or notes. Structured output must reference exactly the supplied facts/rule and contain exactly the approved checks, optionally reordered. Trusted catalog text is rendered; generated prose, measurements, capabilities, new instructions or actions are rejected. Responses are size/time bounded; provider unavailable/timeout/malformed/invalid plans safely retain deterministic checks, with static status codes and no response/exception logging. Explanation results are audited, not stored as confirmed diagnostic evidence. Local-model requests are POSTs to a local explanation service, never device writes. No running model was used for synthetic tests.

## API and bounds

All routes under `/api/rf/troubleshooting` require active operator/admin authentication; viewer/unknown roles fail closed. GET list supports status and bounded pagination; GET `/{id}` returns detail. POST `/evaluate` accepts 1–10 distinct device IDs, requires PostgreSQL and serializes evaluation with an advisory lock. Topology is capped at 10,000 devices/links; SQL statement timeout is 5 seconds; existing analytics detail limits apply. PATCH `/{id}` updates human workflow; POST `/{id}/explanation` returns disabled/fallback or constrained local check ordering. No device credentials/configuration or execution endpoint is exposed.

## Migration, backup and rollback

Migration `0009_rf_troubleshooting` follows `0008_rf_analytics` and adds two workflow tables with a stable-key unique constraint and list/note indexes. It does not modify source telemetry, inventory, analytics projection, existing incident records or collector settings. Run the established release backup first, then `alembic upgrade head` and `alembic check`. Back up configuration privately alongside PostgreSQL using the NOC-84 procedures. Application rollback to NOC-89 may leave 0009 tables intact; do not drop workflow records during routine rollback. If an isolated schema downgrade is required, export recommendations/notes/audit first: `alembic downgrade 0008_rf_analytics` removes the two new tables, then `alembic upgrade head` recreates them. Validate restoration in a disposable database; never overwrite a production database.

## Validation and remaining gates

Synthetic tests cover weak/declining signal, low SNR, suspected interference versus congestion, modulation/capacity decline, disconnects, single/full microwave carrier failures, overheating/alarms, upstream topology cycles, stale/missing/conflicting evidence, cold start, deduplication, observed recovery/recurrence, authenticated workflow/audit, metadata injection, notes escaping, disabled/unavailable/malformed/local-model failures, and rejection of hallucinated facts/actions. Existing NOC-83–89 tests and all CI jobs remain required. Browser workflow uses only existing synthetic historical fixtures.

Before real-device/production use: review the full stacked chain; validate read-only vendor interfaces, firmware capabilities, mapping/units, engineered limits and representative labelled field evidence; tune thresholds and independently validate diagnostic quality; approve incident/retention/notes privacy policy and working failover evidence; size dense-history query/resource budgets; complete inherited bare-VM, signed-artifact, credential/JWT and recovery release gates. Optional model hosting/provider quality/security need separate review. **Synthetic tests do not validate real-radio compatibility, AI accuracy, actual customer impact or production readiness.** No network/RF/routing/firewall changes, production access, deployment or merge is authorized here. Self-healing remains simulation-only.
