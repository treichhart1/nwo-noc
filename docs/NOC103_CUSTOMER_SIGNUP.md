## Architecture and public boundary

One NOC repository and PostgreSQL inventory; no second CRM, asset, tower or work-order model. The private FastAPI app includes `/api/applications` for administrators/operators and narrowly scoped assigned-technician survey context. The dedicated `app.signup.public_app:app` includes only health, public plan configuration, submission and private receipt lookup. It does **not** import/include private routers. Do not put the existing NOC frontend or its reverse proxy on a public host.

The independently built `frontend/dist-signup` contains only the responsive public React application. Run `npm ci`, `npm run build` and `npm run build:signup` in `frontend`. The private application dashboard is `/?applications=home`; related work orders open the existing `/?field=home&work=ID` workflow. The mobile field page retrieves consent-limited contact information from protected application context, not shared work-order descriptions.

`examples/signup/wordpress.html` is a theme-independent iframe/link example for a separately approved **HTTPS** `signup.nwohiobb.com` origin. `examples/signup/nginx.conf` permits only public signup/static paths, caps bodies at32 KiB and supplies CSP with explicit WordPress frame ancestors. The application itself bounds streamed request bodies, validates server-side, requires same-origin signed CSRF cookie/header and exact Origin, and offers no CORS/public admin API. There was no change to the live WordPress site.

## Configuration and activation prerequisites

Everything is disabled by default. See `examples/signup/signup.env.example` and the **example**, unactivated `examples/signup/compose.yml`. Provision a random Fernet master key outside source control, owned by runtime UID10001, mode0600 in a private0700 directory; mount it read-only into private backend and public gateway at `SIGNUP_PII_KEY_FILE`. Do not regenerate an existing key. The standard isolated Compose stack has a persistent `signup_private` volume for synthetic acceptance. `runtime_permissions.py` changes ownership/modes only after checking approved entries; it never replaces a key.

Use a separate restricted PostgreSQL login inheriting `examples/signup/public-role.sql`; never give the public process the private NOC database owner/runtime role. Review existing PUBLIC grants. The public role needs no customer, user, topology, quote, document or work-order privileges. Use a separately approved firewall/egress proxy: public gateway may reach only PostgreSQL and the exact Cloudflare verification service; block management/RFC1918/device networks and arbitrary internet destinations. Do not add public ingress to the offline release-validation stack. The sample Compose file is an operator review template, not an activated secure perimeter.

For real Turnstile, set mode `turnstile`, site key, private secret file and exact public HTTPS origin/expected hostname. Server verification calls only Cloudflare's documented `siteverify` endpoint, requires `service_signup` action, correct hostname, recent challenge, TLS and bounded timeout. An independently hosted form needs its hostname configured in Turnstile. Synthetic fixture mode requires explicit offline staging + synthetic monitoring + public test mode. It cannot be used as a production spam control. Actual Cloudflare/WordPress integration has not been tested.

PostgreSQL-shared 15-minute budgets limit CSRF config, submissions and lookup, plus a global cap. Client addresses are HMAC indexed. Forwarded IP is ignored except from explicitly trusted proxy CIDRs and only for a single valid IP. Configure trusted proxies carefully and enforce edge limits too; NAT/shared ingress budgets can otherwise intentionally throttle legitimate users. Application payloads and tokens must be excluded from access/APM/error logs. Run the public gateway with `--no-access-log`.

## Data, privacy and retention

Thirteen normalized tables store catalog, documented coverage, applications, immutable history/qualification/surveys, work-order associations, quote versions, draft notifications/provisioning, encrypted photo references, public budgets and CAPTCHA use receipts. Indexes cover state/age, assignment, plan, exact normalized contact/address hashes and related history. Private list pages are bounded50; plan/area collections100; event history50; qualification20; surveys/quotes50. Matching is bounded to5000 imported service locations and reports uncertainty rather than scanning networks.

Applicant identity, addresses, consent, notes, survey details, change reasons and manual acceptance evidence are encrypted with a random per-application key wrapped by the private master key. Lookup/contact/address indexes use keyed SHA-256; no plaintext customer contact goes into generic work orders or global audit reasons. Assigned technicians see only their linked work context and consent-permitted email/phone, not billing, quote or duplicate-customer records. Administrators/operators can review applications; viewer and unauthenticated roles cannot. Customer quote amounts are restricted to application staff.

Opaque lookup tokens reveal coarse status only; no name/email/address, quote, tower, network IP or topology. Unknown tokens get a generic unavailable status. Retention defaults365 days (configurable30–3650): administrator redaction requires a closed, aged application without legal hold. It destroys the wrapped key, lookup/contact/address indexes and primary ciphertext; encrypted history/photos then become unreadable. Operational references remain for audit. Backup copies require independent retention/erasure procedures. No automatic retention purge, bulk budget cleanup or unattended customer messaging is enabled; monitor table growth and implement approved archival operations before sustained public use.

## Qualification and Powercode

Addresses are normalized without silently dropping apartment/unit information. Public submissions require US physical service addresses, contact format, explicit privacy consent, audience-compatible active public plan and optional channel-specific consent. Exact submission UUID/body retries return the same receipt; changed payload with an existing key is rejected. Duplicate people/addresses are review suggestions; applications are never silently merged.

Internal qualification accepts source-labelled coordinates or an explicitly approved, allowlisted Nominatim-compatible `/search` provider. Geocoding is off by default, uses TLS/timeouts/bounded retry, refuses ambiguous responses and requires explicit address-transfer approval. No geocoding was performed against a real provider. DNS checks alone are not a replacement for an approved egress proxy/firewall. Geographic distance, sector azimuth/beamwidth, documented frequency/capacity, fresh tower-health context, coverage polygons, planned/active fiber/hybrid areas and approximate straight endpoint-to-endpoint fiber distance are explainable evidence. Straight-line fiber distance is not a surveyed route, splice/port availability or connection entitlement. No terrain, obstruction, LOS, predicted signal or available RF capacity is invented. Missing evidence requires survey; nearby towers/fiber never guarantee service, construction cost or date.

Powercode matching reads existing imported account/service/plan references and tower/sector inventory only. Exact contact or normalized address evidence yields suspected matches; administrator confirmation is separate. Existing customer opt-outs suppress SMS drafts. Provisioning preparation creates an approved **documentation-only** record; there is no Powercode account-write/activation operation. Live Powercode is never contacted.

## Lifecycle, surveys, quotes and work orders

States: submitted → under_review → qualification_pending/site_survey_required → survey_scheduled/qualified → quote_pending → quote_sent → customer_accepted → installation_pending → installation_scheduled → installed → activation_pending → completed. Rejection/cancellation and explicit review returns are supported where validated by the transition graph. Qualification needs administrator review evidence; quote approval/issue/manual acceptance are administrator actions with immutable revisions and expiry. Unknown charges block approval; explicit zero is permitted. No historical plan price/speed is assumed; synthetic test prices are fixtures only.

State changes use expected revision checks and idempotent operator operation keys. Installation/survey work orders reuse NOC-101. Each application/kind has one unique association, and transactions serialize changes with existing inventory/field locks. Technician/site/sector/fiber references are checked. Installation requires approved application state/site; documenting installed requires completed linked installation work. Activation/completion require explicit acknowledgement that this is documentation, not provisioning. Cancelling/rebooking an existing work order is performed in that work order, not by generating duplicates.

Survey observations are encrypted, timestamped and tied to the assigned work order. Supported PNG/JPEG photos undergo actual content/CRC/type/size validation (512 KiB,20 per survey), SHA-256 verification and private immutable file storage; bytes are additionally encrypted under the applicant key. Retrieval needs assignment/staff authorization, a trusted clean scanner result and explicit admin approval (`POST /api/applications/photos/ID/approve`). Default scanner state blocks retrieval. Use NOC-102 ClamAV integration before actual uploads; synthetic clean scans establish no malware protection. No public attachments or customer self-service quote acceptance portal is provided.

Notification templates cover receipt, information, survey, quote, installation and status. They reuse NOC-96 consent/opt-out concepts as internal drafts without fabricating incidents or creating delivery jobs. No SMS, email, phone or Slack delivery occurs. Legal agreements, payment collection, dispatch, network/IPAM configuration and automatic service approval are absent by design.

## Backup, restore and rollback

Take the existing PostgreSQL custom-format backup plus a separate encrypted backup of `signup_private/pii.key`, the NOC-102 document store (including encrypted signup photos), environment/secret configuration and the exact image/commit manifest. Back up the key separately with restricted access; loss prevents recovery of applicant data. Do not put key bytes into SQL dumps or logs. Restrict and encrypt PII backups; test restoration on a fresh isolated database and private file volume, verify checksums and a known synthetic application's decrypted identity, photo checksum and quote/work history. Preserve source data. Key rotation requires explicit rewrapping and HMAC reindexing; automated rotation is not implemented.

Before migration disable public submissions and operator changes, back up and run `alembic upgrade head` with the migration role. Confirm `alembic check` and heads. Migration0022 adds tables/triggers, leaves upstream migrations and inventory intact. Code rollback should disable the signup gateway and keep schema0022/data/key/blobs, then restore the prior images; do not run a data-dropping downgrade on a populated system. The0022→0021→0022 downgrade test is for disposable empty schemas only. Recovery from a failed upgrade restores into a **new** database; never overwrite production or the source acceptance database.
