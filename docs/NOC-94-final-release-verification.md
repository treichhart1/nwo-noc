## Fixes and security findings

- JWTs now use PyJWT with explicitly restricted HS256, issuer/audience/type, expiry/issuance bounds, random session IDs and immutable user-ID binding. Default lifetime is 15 minutes, supported range 1–30. Legacy RC.2 tokens are invalid after upgrade: reauthenticate. Malformed, oversized, wrong-context and invalid tokens fail closed.
- `POST /api/auth/logout` persists the presented session's revocation in PostgreSQL; raw JWTs/passwords are not stored in revocation or audit records. Other sessions remain valid. React waits for server revocation before claiming logout; if storage fails, retry rather than pretending revocation succeeded. Role/active-user changes are checked on every authenticated request. Database failure denies authentication.
- Migration 0012 adds only indexed revocation metadata. Retain revocations through their expiry; apply a reviewed bounded expiry-retention operation as part of maintenance. On **any database restore/rollback**, rotate the signing secret and reauthenticate users before serving traffic: restoring an older revocation set must not resurrect an unexpired token.
- Backend/worker images run as UID/GID 10001; frontend nginx runs as 101 on internal port 8080. The isolated release profile uses read-only root filesystems, writable bounded `/tmp`, dropped capabilities and no-new-privileges. Narrow UID-owned temporary cache/PID mounts also support the retained old nginx image during isolated rollback without granting root/capabilities; low-port binding is allowed only inside that frontend network namespace. HTTP access remains loopback-only through the existing relay; PostgreSQL/Redis are unpublished and the network is internal-only.
- Application backend/worker use `noc_app`: no superuser, database/role creation, replication, RLS bypass, privileged role membership, persistent schema DDL or temporary-database privileges. The isolated migration/bootstrap account remains separate. The runtime environment clears its bootstrap database password; only its own restricted database URL remains. Restore grants are reconstructed in the newly created recovery database, without altering the source or overwriting an existing target.
- The database/bootstrap and spool ownership helpers operate **only on generated isolated acceptance state**. The one-shot root helper receives narrowly scoped filesystem capabilities, migrates only private recognized spool files, rejects unexpected/symlink/world-accessible entries, and never rewrites payload contents. Workers/writers must be stopped before ownership migration. Private credentials/mappings for a future nonroot pilot must be owned by the reviewed runtime UID and mounted read-only.
- `POST /api/monitoring/reliability/emergency-disable` is administrator-only. It fsyncs a persistent private stop latch shared by backend/worker **before** auditing. New scheduler claims, TCP checks, read-only HTTP operations and radio/microwave collector attempts stop. Already in-flight reads may finish within existing bounded timeouts. No device commands or RF changes occur. Operator stops cannot be classified as RF/device outages. The UI exposes the stop state and admin control.
- There is deliberately **no remote enable/clear route**. If authentication/database/storage is unavailable, use the approved local worker-stop and external egress/credential disable procedure. A failed audit after successful latch creation reports that the stop is active; preserve the latch and repair audit storage. Clearing it requires separately approved offline operator recovery with workers stopped, preserved audit/outbox evidence and verified endpoint restrictions.

## Dependency advisory audit

The old RC.2 image is used only inside the isolated rollback rehearsal; its known dependency flaws are not approved for live pilot traffic. General internet-facing abuse/rate-limit, host hardening and external security review remain necessary before broader exposure.

## Ubuntu 24.04 installation and RC.2 upgrade/rollback

Use a fresh disposable Ubuntu 24.04 environment, generated private acceptance state and local Docker daemon. Follow [the installation guide](NOC-84-installation-and-recovery.md), this update, and [NOC-93 release procedures](NOC-93-release-readiness.md). The supported hardened rehearsal profile is `deploy/compose.isolated.yml`; normal docker-compose.yml remains development configuration, not an enforced egress or production-security policy.

Installation now starts isolated db/Redis, provisions the restricted runtime role/default grants, prepares private volume ownership for the image's reviewed UID, then runs owner migrations and starts the nonroot application services. Reinstallation reuses the same private state; it does not rotate initialized database passwords. Capture all four immutable image IDs/source/configuration hash with `pin_images.py` after committing the candidate and loading its images. A changed configuration/image requires a new reviewed candidate state; never silently repin.

A fresh configuration includes `APP_DATABASE_PASSWORD`, `NOC_RUNTIME_DATABASE_URL`, `NOC_FRONTEND_INTERNAL_PORT=8080`, and a short session lifetime. Never reuse test credentials. Older private configurations need an explicitly reviewed new candidate configuration preserving the existing database owner identity and adding the restricted role; do not attach freshly generated passwords to an existing volume. The generic development Compose path is not a substitute for this role/bootstrap workflow.

`rehearse-upgrade.sh NEW_STATE` now archives actual RC.2 commit b532950, creates schema0011 with synthetic records and a private old-format outbox delivery, rejects an injected DDL failure after an explicit checkpoint and unsafe startup, rolls back to the old release, then migrates ownership and upgrades to RC.3/schema0012. It verifies payload hashes/UID readability, authenticated operations, data/findings, restarts, isolated old-backup recovery with actual old images and preservation of the current database. Old frontend port80 and new port8080 are recorded separately. No database is downgraded or existing restore target overwritten.

Rollback remains a **new isolated matching-image/database restore**, not starting old code against an unknown newer schema. Preserve failed volumes and pending outbox, stop writers, revoke external pilot access, restore a verified backup to a new target, rotate signing keys, verify runtime grants/auth/data/audit/outbox consistency, and obtain separate traffic approval. A previous vulnerable image is an offline recovery aid, not permission to resume live monitoring. Do not delete pending telemetry or unreviewedly replay it into a different restored dataset.

Ubuntu container/userspace acceptance does not certify bare VM boot/reboot/systemd/firewall behavior or off-host encrypted recovery. Those remain external prerequisites.
