# NOC-91: RF operations and technician investigations

Builds on draft NOC-90 #94 at `b343c39a9b58ccb1a720c2c4aaaabe2b55008e68` (CI #452 passed). The full NOC-83–90 dependency chain remains stacked and unmerged.

## Operator experience

Open **RF Operations**. The page combines stored normalized RF observations, analytical alerts, tower/POP inventory, backhaul endpoint evidence, access sectors, collection status, incidents and saved NOC-90 recommendations. Nothing polls or configures equipment, projects telemetry, launches models, or performs remediation when this page opens.

Apply site/tower, vendor, literal device/link name or ID search, alert severity, incident status and 1h/24h/7d/30d filters explicitly. Typing does not request new dashboard data. Device pages contain at most 50 entries in the UI (API maximum 100); related incidents have independent 25-entry pages. Link and sector context lists cap at 100 and report truncation; narrow site/search filters for larger inventories. Site options cap at 1,000 with an API truncation marker. Managed inventory has a 10,000-record bound per inventory table; exceeding it produces an actionable error, not partial fleet counts.

The fleet summary reports **latest measured exceptions and coverage within the inventory filters**, not a fabricated overall RF score or sustained alert count. A device without projected RF is unknown, including non-RF devices. Site RF and independent reachability coverage are distinct. No recorded exception does not prove complete health. Analytical alerts and saved recommendations apply to the current device page; severity filters those page alerts and the related incident list. The scope is stated on screen. Large fleets must page through analytics rather than treating a partial page as a fleet-wide absence of alerts.

Site focus includes equipment, associated links/sectors, stored RF health, related incidents, and documented upstream/downstream device dependencies. Probable upstream outages remain unconfirmed; shared monitoring/power failure and incomplete inventory remain alternatives. Potential downstream **devices are not subscribers**. Redundancy remains unknown until independently validated.

Link detail loads on demand, for at most two documented endpoints. It reuses historical analytics and charts with mapping/channel/site/link context and gap preservation. It shows signal/RSL, SNR, noise, channel information, modulation, capacity, directional throughput/utilization, reported alarms, score, evidence quality and source observation timestamps. Explicit source links differing from the selected inventory link are labelled and excluded from that link's alert context/chart. An unspecified source link is endpoint context, not proof of a particular wireless path. Unsupported, missing, invalid, stale and future data stay distinct; absent alarms are not assumed clear. Link endpoint aggregate health excludes RF series explicitly associated with another link.

**Last usable telemetry** is a successfully normalized source observation timestamp, which may now be stale. **Last successful poll** comes from a successful collector audit, and remains unrecorded for export-only fixtures. A successful source/export normalization is not invented as a successful live poll. Collection errors use static allowlisted codes; raw error strings/configuration/credentials are not returned.

The new view has manual refresh and cancels obsolete reads when filters change. The legacy shell's 30-second polling is suspended while RF Operations is open. It retains its initial application bootstrap load. Historical chart/detail queries occur only when requested. All displayed operator times use America/New_York.

## Existing incidents, assignment and audit

Investigations are existing `incidents`, not a second case-management system. Opening an investigation from an active stored RF alert revalidates its exact observed timestamp and reuses an active incident anchored to the device/link. A global bounded advisory lock serializes these contextual opens, preventing duplicate contextual incidents. An already resolved prior investigation requires newer observed evidence before another contextual incident can be opened. Operators may still intentionally create incidents through the existing general incident workflow.

Alert acknowledgments refer to **the reviewed observation timestamp**. New telemetry is marked "new telemetry since review", not silently acknowledged. These are source observations, not an inferred alert episode or confirmed recovery. Saved recommendation episodes/acknowledgments continue to use NOC-90's independent evidence and lifecycle controls.

Active operators/admins can assign an investigation to an active operator/admin, acknowledge it, investigate, enter findings and timestamped technician notes, resolve it and close it after documenting resolution. Existing open/acknowledged/resolved behavior is retained; investigating/closed extend that workflow. Closed investigations cannot be silently reopened, and they are excluded from existing active summaries and RF correlation. Synthetic incident recovery increments the same revision counter.

The RF UI always sends `expected_revision` when saving. A row lock and revision conflict reject stale edits without saving their notes. Refreshing after a conflict requires an explicit reload; unsaved text is retained on error. Legacy clients may omit the revision for compatibility, so a full deployment-wide concurrency policy remains an integration consideration. Forms are disabled during saves to avoid losing edits during asynchronous refresh. Resolution/notes are operator-entered evidence, clearly distinct from measured facts and AI explanations. Never put credentials into findings/notes; obvious secret assignments, private-key markers and control characters are rejected. Notes render as plain React text.

Incident notes and audit trails use ascending ID cursors with at most 100 records/page and explicit continuation, permitting review of the full retained history. The `/api/rf/operations/audit` endpoint also supports the existing recommendation and observed-alert audit types. Sensitive keys/obvious credential assignments in legacy audit details are redacted. Audit actions retain actor, time, source evidence and changed fields; note bodies remain in the note history. This is retention-bounded history, not an immutable external audit ledger.

NOC-90 recommendations and safe checks are reused directly in the Recommendations view. No duplicate recommendation engine is introduced. Optional local explanations retain NOC-90's disabled-by-default, offline-forbidden, constrained-output architecture. No model-generated prose or equipment controls are added.

## API, database and security

All `/api/rf/operations` routes require an authenticated active operator/admin; viewer/unknown roles fail closed. Read routes include overview, site/link detail, eligible technicians, shared incident detail/notes and cursor audit. POST `/alerts/review` accepts only a canonical derived alert key, an aware observed timestamp and acknowledge/open-incident operations; it verifies current stored evidence and handles changed evidence with a conflict. Incident updates use the existing authenticated PATCH `/api/incidents/{id}` route and shared update service. No equipment command or secret configuration endpoint exists here.

Migration `0010_rf_operations` follows `0009_rf_troubleshooting`. It adds incident assignee/findings/closure/revision fields, incident notes, observation acknowledgments and query indexes. Existing telemetry, projections, incidents, recommendations and migrations remain intact. Reads are batched, inventory/payload bounds are explicit, SQL has 5-second statement timeouts, and database failures roll back and return a static 503. A later successful read can reconnect normally. The existing incident list's per-record inventory lookups are replaced with at most four SELECTs for its bounded list.

Back up using NOC-84 procedures before upgrading, then run `alembic upgrade head` and `alembic check`. Prefer application rollback with additive tables retained. A schema rollback to 0009 drops only the new fields/tables/indexes: export assignment/findings/closure, notes, acknowledgments and audit first, and finish/reconcile investigating/closed incident statuses with a reviewed old-client compatibility plan. No silent status conversion or production overwrite is performed. Restore into a disposable database before any approved real recovery; source data must remain untouched.

Existing NOC-83–90 tests remain required. Browser acceptance covers the unified dashboard, explicit filtering/search, site context, shared incident assignment/lifecycle, recommendation acknowledgment, historical link charts, injection escaping, no hidden polling, and responsive empty/stale/missing states.

`python -m app.rf_operations_benchmark` requires offline staging and disposable database `nwo_noc`. Each 500/1,000-device dataset has 40 sites, 39 links, 80 sectors, 5,000 incidents and 48 directly seeded projection points/device across 30 days. It uses an owned random schema, never changes public data, and removes only that schema afterward. It records service/query counts, HTTP/ASGI API serialization/latency, link/chart queries, four concurrent operator sessions, the legacy incident list and reconnection after disposing idle connections. Gates are ≤20 overview SELECTs, ≤4 legacy list SELECTs, <5-second ordinary/chart requests and <10-second concurrent maximum. These are synthetic same-host measurements, not dense ingestion, WAN latency, cold-cache production SLAs or field accuracy. Measured results and exact counts belong in the draft PR/CI evidence.

Existing 250/500/1,000-device worker checks are preserved. Release acceptance additionally checks the new RF API after actual worker/service and database restarts. Ubuntu 24.04 userspace installation, backup/restore and existing RF/browser fixtures remain part of CI; a bare-VM installation remains a separate release gate.
