## Architecture and persistence

The `app.notifications` package separates contracts/policies, private PostgreSQL models, templates/targeting/approvals, interchangeable providers, encrypted secret storage, API and durable queue worker. PostgreSQL is the authoritative outbox, attempt/dead-letter history, scheduling and deduplication store. Redis remains existing monitoring infrastructure and is not required for notification durability; a Redis restart cannot lose a notification job.

Plans persist a minimized immutable approval snapshot: source lifecycle/revision, explicit topology and paths, selected customer/service IDs, eligibility/suppression reasons, HMAC contact fingerprints, templates, policy and rendered nonpersonal content. Phone/email/customer names are not copied into notification queues or Slack payloads. Recipient numbers are read transiently from private NOC-95 storage immediately before mock processing, with row locking and current consent/opt-out/phone checks. Providers do not retain numbers or bodies in call logs.

A draft has no deliveries. Operators explicitly approve the content, scope, recipients, timing and estimated cost. The API requires both confirmation and the **fingerprint of the reviewed draft**; stale previews cannot approve replacement content. Source/policy/template/consent/mapping changes invalidate approval instead of silently expanding recipients. Customer reconciliation and queue claims use bounded PostgreSQL transaction advisory locks; delivery rows also use `FOR UPDATE SKIP LOCKED`. Batches are bounded. The existing monitoring worker can run notification processing on a dedicated single thread, preserving RF claims/heartbeats and isolating collector failures.

Delivery states are `queued`, `retry`, `simulated`, `dead_letter` or `suppressed`. Retries use 5s exponential backoff capped at300s and a configurable maximum1–5 attempts (default3). Permanent failures go directly to dead letter. A dead letter can receive one explicitly approved mock retry against unchanged approved context, preserving its attempt history. Completed simulations cannot be retried. If evidence/context is stale, do not bypass it: obtain fresh operator review and an appropriate new follow-up plan. There is no automatic reapproval or resending after cancellation.

Mock receipts, state and attempts commit in one PostgreSQL transaction. A crash or DB interruption before commit rolls back the claim; a fresh process resumes the same durable row. Receipt keys are deterministic. This is **not an exactly-once claim for future real external APIs**: an ambiguous real send would require provider-specific idempotency/status reconciliation before any retry. No real adapter is allowed to masquerade as a mock sender.

## Provider methods and credentials

- `Sender` is the interchangeable outbound interface. `MockSender` emits deterministic simulated receipts and bounded synthetic failures without any network transport.
- `TwilioMockAdapter` prepares Twilio Messages resource form/Basic-auth shapes at a **synthetic** origin using required `httpx.MockTransport`. It validates account/message SID shapes, E.164 destinations, bounded token/body, accepted statuses,429/auth/server/malformed/timeout behavior. It does not connect to Twilio, establish carrier deliverability or prove an actual account's permissions/pricing. Real HTTP transports are rejected.
- `MockSlack` prepares webhook or supported `chat.postMessage` JSON shapes against a synthetic origin, requires MockTransport, verifies request bounds through private application input, and handles rate/auth/response/timeout failures with static error codes. TLS verification is true, redirects/environment proxies disabled. No live workspace, webhook or OAuth token is used.
- Slack technician payloads include incident/maintenance ID, infrastructure name or explicit target ID, event/kind/severity/detection time, estimated potentially affected account count, downstream site IDs, allowlisted finite RF metrics, suspected/confirmed evidence and an incident link. Customer fields and arbitrary raw telemetry/credentials are excluded; contact-like text and mentions in inventory names are redacted. Unfurling is disabled. Configure policy `dashboard_base_url` as an approved HTTPS origin for future absolute Slack links. Empty means only a relative internal NOC link; it is not a usable cross-workspace production link. URLs with userinfo, queries, insecure schemes or arbitrary paths are rejected.
- Provider credentials can be stored by administrators through `PUT /api/notifications/credentials/sms|slack`. Values are SecretStr/size bounded, encrypted using authenticated Fernet encryption, never returned/logged and unused for live delivery in this milestone. The key comes from `NOTIFICATIONS_VAULT_KEY_FILE`: regular file, owned by runtime UID, mode0600 or stricter, maximum256 bytes; symlinks/public files are rejected. Generate a Fernet key privately and mount it read-only for UID10001. No generated/default production key is committed. Back up the key separately under approved encryption/access controls; test resealing/rotation before enabling any future provider. No credential-decryption API exists.
- There is no public provider delivery/status/STOP callback route. The bounded timestamp/HMAC helper is explicitly a **mock callback protocol**, not a substitute for Twilio/Slack's native signature validation or legal opt-out handling. Future native callbacks must implement the selected provider's documented signatures, replay/event-ID dedupe, destination/account ownership and verified STOP delivery before live activation.

## Configuration and safe processing

Defaults:

```dotenv
NOTIFICATIONS_WORKER_ENABLED=false
NOTIFICATIONS_AUTO_DRAFTS_ENABLED=false
NOTIFICATIONS_LIVE_DELIVERY_ENABLED=false
NOTIFICATIONS_VAULT_KEY_FILE=
```

Mock worker enablement requires `APP_ENV=staging` and `OFFLINE_MODE=true`. Setting `NOTIFICATIONS_LIVE_DELIVERY_ENABLED=true` fails startup even with stored credentials. This branch provides no live activation path. Auto-drafts are separately disabled; enabling them only creates suspected drafts from active incidents, never approval or delivery. The durable worker supports a one-pass rehearsal with `python -m app.notifications.worker`; explicit manual mock processing is available to administrators in offline staging. The safe provider test uses a reserved synthetic recipient and mock Slack channel, no customer lookup or external delivery.

Administrator policy covers timezone, outage hold, quiet hours, per-plan/minute/hour/rolling24h/per-customer caps, event storms, attempt limits, optional unit price and rolling24h budget, Slack severity/channel/escalation and content retention. Unknown unit price is displayed as unknown; it does not imply free real messaging. Live activation would require validated provider prices and spending limits.

The defaults hold brief incident SMS for300s, cap SMS at100 per plan,20/minute,200/hour,500/rolling24h and3/customer/day, and cap drafts at20/hour. Queue reservations include pending work conservatively. The worker rechecks actual delivered simulation counts and costs before each SMS, so deferred jobs cannot bypass caps. Costs use conservative UTF-16 segment estimates in USD microunits and BigInteger totals; they do not predict actual GSM7/UCS2 carrier encoding, tax, fees or invoices. No silent truncation is permitted when a recipient set or cap is exceeded.

## Customer targeting, event accuracy and templates

Targeting uses NOC-95 `analyze` and consent-aware recipient selection. It preserves explicit site/AP/sector/fiber dependencies, recorded redundant paths, stale/unknown mapping states, global shared-phone suppression, account/service status and contact freshness. Customer ID dedupe prevents multiple services generating multiple messages. A changed phone invalidates prior consent through NOC-95. Operators can add local compliance/opt-out holds; removing a hold never re-grants consent or clears an opt-out. There is no marketing campaign/category or marketing consent reuse.

Supported evidence types cover backhaul outages/severe degradation, tower power/UPS/service interruptions, AP/sector/fiber/equipment outages, planned maintenance and restoration. Suspected conditions, brief telemetry interruptions and UPS warnings can prepare technician/internal alerts without customer SMS. Customer-outage selection requires explicit operator-confirmed impact evidence and the configured duration hold. An evidence reference is mandatory; numeric RF fields are bounded and optional. No missing measurement is treated as zero or an outage.

Topology loss can identify **probable** upstream incidents and report them to technicians; it never declares definitive root cause or silently merges independent incidents. Remaining/unknown redundant paths preserve uncertainty. Per-customer outage cooldown and duplicate event keys suppress repeat messages across related upstream/downstream alarms. Unknown associations cannot be overridden by entering customer IDs: fix/review the inventory in NOC-95, then prepare and approve again.

Templates support initial outage, update, extended outage, planned maintenance, rescheduling, cancellation and restoration. They require `{brand}`, `{support}`, `{opt_out}` and allow only `{event_id}`, `{window}` additionally. Branding is Northwest Ohio Broadband, support text **419-954-0586**, with STOP guidance. Formatting attribute access/conversions/private customer fields are forbidden. Default messages do not promise repair times. No AI model generates notifications or repair estimates; administrator template edits plus operator approval cover any manually authorized information. A future legal review must define service-notice exceptions, consent/quiet-hour/compliance policy before actual messaging.

Restoration requires a resolved/closed incident or completed maintenance, a nonfuture completion, at least3 independently verified recovery samples and operator evidence verified within5 minutes. Only customers with a prior simulated notice for the same context can receive restoration/cancellation simulations; current consent/eligibility still applies. Incident closure alone is not proof of service restoration. Quiet-hour deferral may cause verification to become stale; the worker suppresses rather than sends a false recovery. A future native pilot must bind evidence to trusted monitoring observations and define the reviewed follow-up/revalidation procedure.

## Operator dashboard and planned maintenance

**Notifications** shows source incidents, plans, queued/retry/dead-letter/suppressed/simulated counts, provider mode, schedules, eligible/suppressed recipient totals, templates, conservative costs, deliveries and paginated audit history. Recipient pages expose only internal IDs/reasons and full aggregate counts; approval applies to the full fingerprinted set, never a silently truncated preview. Incident links open the existing RF technician investigation directly. All notification data and actions require current active operator/admin access; provider credentials/policies/templates, mock processing/tests and retention controls require administrator access. Unauthorized access is audited by the shared private-data authorization gate.

Workflow:

1. Review the incident or select tower/POP, AP, sector, backhaul/fiber for maintenance. Supply an evidence reference and distinguish suspected from confirmed customer impact.
2. Review recipient scope/reasons, template, cost, confidence and source freshness. Resolve unknown mappings in Customer Impact; do not assume estimated affected count equals contact-eligible count.
3. Select a scheduled time or immediate processing. Maintenance input, messages and quiet hours use the **configured IANA timezone**, independent of browser location; UTC timestamps are stored. The local-time API rejects DST gaps/repeated ambiguous wall times and stale timezone settings. Direct APIs may use explicitly offset aware timestamps.
4. Confirm the fingerprinted preview and approve **simulation only**. Drafts never enqueue messages. Actual messaging remains unavailable regardless of this confirmation.
5. Inspect mock outcomes, static errors and audit. Cancel pending plans if needed; queued retries and dead letters do not imply delivery. Use an approved retry only while the original context is current.

Site/link maintenance created here also creates a linked existing Operations maintenance window, preserving existing suppression semantics. AP/sector schedules remain explicitly narrow; they do not invent a network-wide/tower suppression window in the legacy model. Cross-UI changes to linked Operations status/timing invalidate notification context. Reschedule/cancel/complete uses revision checks and suppresses old pending notices; new lifecycle notices require new review/approval. Completion before the scheduled start is rejected. Existing pre-NOC-96 maintenance records are retained; adopting/migrating their notification metadata needs explicit operator review rather than automatic recipient messaging.

## Auditing, privacy, retention and recovery

Plans/approvals, source/recipient policy outcomes, suppression changes, retries, static provider errors, simulated receipts, templates/policy/credentials, retention and operator access are recorded with actor/time/internal IDs. Raw contacts, secrets, search text, source/customer names and arbitrary provider errors never enter notification logs. Source addresses/names remain private in NOC-95, not Slack. Do not enable proxy/request-body/Authorization logging. `simulated` means mock processing only.

A bounded administrator retention action redacts old terminal plan bodies, snapshots/evidence, contact fingerprints and service arrays after the policy interval (default30d). It preserves event dedupe keys, outcome/attempt/audit IDs and accounting timestamps so redaction cannot resurrect a campaign or bypass caps. These retained identifiers still require approved access/retention and data-owner review; this is not legal erasure certification. Pending work is never purged by retention. Real customer data, raw dumps, credentials and screenshots must not be attached to public issues/PRs.

PostgreSQL transactions/outbox survive Redis or worker restart. Existing monitoring DB connection bounds/pre-ping remain. No network equipment is restarted or changed. If storage fails, keep the queue and private state, recover DB and resume a mock worker; never reset attempts/receipts or bulk reapprove blindly. The acceptance workflow restarts actual isolated DB and worker containers with queued notifications and runs independent worker processes twice, asserting unique receipts and no duplicate attempts.

Before migration0014, take an approved private backup. Use the owner migration service and preserve NOC-94's restricted runtime role/default grants, nonroot/read-only containers, private volumes, internal-only networks, immutable manifests and RF simulation-only controls. Restore only into a new isolated database with matching images and rotate JWT signing keys/re-authenticate before traffic as documented in NOC-94. Contact HMACs/approval context may become invalid after key rotation: require renewed review; do not force pending messages through. Real external outbox restore additionally requires provider reconciliation to prevent historical messages replaying after a backup—currently unverified and blocked.
