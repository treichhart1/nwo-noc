# Telnyx setup and acceptance

Official contracts reviewed: [send message](https://developers.telnyx.com/api-reference/messages/send-a-message), [receiving webhooks](https://developers.telnyx.com/docs/messaging/messages/receiving-webhooks), [messaging error codes](https://developers.telnyx.com/docs/messaging/messages/error-codes), [advanced opt-in/out](https://developers.telnyx.com/docs/messaging/messages/advanced-opt-in-out), [API errors](https://developers.telnyx.com/docs/development/api-fundamentals/api-errors).

Use the ProviderInput JSON in TWILIO.md, selecting Telnyx, replacing account_sid with the **organization UUID**, service_id with the **Messaging Profile UUID**, and callback_url with `https://<approved callback host>/callbacks/sms/telnyx`. These shared field names are NOC normalization; they do not imply Twilio SID semantics. Keep enabled/callbacks false, price unknown and spending caps zero until separately reviewed. Choose owned E.164 sender and configured categories/allowlisted recipients; no guessed prices.

The write-only password control accepts exactly `api_key` and `webhook_public_key`. The API key authenticates Bearer requests to fixed HTTPS api.telnyx.com/v2/messages. The webhook public key is base64-encoded raw32-byte Ed25519 from the approved Telnyx account. It is separated from outbound credentials in encrypted callback storage. Never store an Ed25519 private key or Telnyx API key in callback metadata. Registration, A2P10DLC/toll-free requirements, sender ownership, messaging profile/organization and provider opt-out policies require operator validation.

Configure POST JSON webhooks to the exact isolated URL with no redirects/query. Verify `telnyx-signature-ed25519` over `telnyx-timestamp + "|" + exact raw body`, clock tolerance300seconds. Accurate host UTC/NTP is required. Native event UUID and signed body hash prevent duplicate/replayed processing. Organization, profile, E.164 endpoint, messageUUID and inbound/outbound direction must match. Retries do not authorize resending the original SMS.

Supported events are message.received, message.sent and message.finalized. Recipient statuses preserve native queued/sending/sent/delivered/delivery_failed evidence; delivery_unconfirmed remains reconciliation_required. STOP applies globally; START/HELP are review-only. Telnyx messaging error **40300** is an opt-out block according to the dedicated error reference/API catalog. A generic receiving-webhook example has conflicting descriptive text; this implementation uses the scoped error-code contract, not that example's text. Errors are preserved as codes, not private response bodies.

Submission sends SMS type, one recipient, approved From, profile and webhook URL. GET /v2/messages/{UUID} provides explicit read-only reconciliation; it must match organization/profile/sender/destination. Operator-supplied missing receipt reconciliation also verifies exact approved content and creation window; wrong/unknown receipt never permits failover. No submission idempotency guarantee is assumed. HTTP429/rejection may be safely bounded; ambiguous failures quarantine.

Use the shared activation procedure and independent per-message approval. Secondary Telnyx must independently meet sender registration, recipient allowlist, category, consent, pricing/caps, host authorization and current config revision. Never switch after Twilio acceptance, timeout or missing callback. Disable sending without disabling verification of outstanding callbacks. Keep historical keys/negative-consent evidence and encrypted backups; no automatic database downgrade. Actual provider send, carrier delivery, webhook and billing compatibility remain NOT TESTED here; no live acceptance claimed.
