## Public/private architecture

The private NOC API is `/api/customer-status/v1`. Existing administrator/operator
roles can review source cases and recipient evidence; administrators alone approve
public names, publication, baseline status, policy and SMS decisions.

The public ASGI application is **`app.customer_status.public_app:app`**, with only:

* `GET/HEAD /public/network-status/v1` — approved, allowlisted status.
* `GET /health` — gateway-process readiness, not a network-health claim.

It never mounts the private NOC router, authentication, customer lookup, signup,
topology or notification callbacks. Do not proxy `app.main` or private APIs to the
website. There is no public incident-by-internal-ID lookup or customer enumeration.

Eight additive tables in migration `0028_customer_status` record policy, approved
public areas, canonical source associations, immutable revision content, immutable
recovery assessments, append-only events, native notification-plan references and
short-lived hashed rate counters. No second incident, customer, work-order or
network-topology database is created. The current public revision has a canonical
FK; publication queries additionally verify the revision belongs to its source case.

The `noc_public_status` security-barrier views expose only explicitly approved
public payload fields. Public identifiers are random stable UUIDs, not incident,
tower or customer IDs. Private source text is never copied into drafts. Generic
service-area names require administrator approval and are snapshotted into a
revision. Titles/descriptions are plain text; HTML, URLs, contact/address patterns,
network addresses and coordinate patterns are rejected. This is defense in depth,
not a replacement for human privacy review of prose or names.

Public data: status, generic title/description/areas, approved maintenance window,
explicitly approved restoration estimate and public update timestamps. It excludes
private tower names/coordinates, IPs, topology, customer contacts/counts, credentials,
internal IDs, diagnostic evidence and financial data.

## Workflows

### Public publishing

1. Select an existing native incident or NOC96 maintenance source. NOC97 continues
   creating/updating internal incidents from monitoring evidence; there is no new
   detector or automatic public publisher.
2. Write a private draft and select approved public service areas. Explicitly review
   privacy and any supplied restoration estimate. Do not invent an ETA.
3. Request approval. An administrator approves or rejects the immutable revision.
4. An administrator explicitly publishes the approved revision. SMS remains separate.
5. Every update, resolution or withdrawal requires a new revision and approval.

States include draft, pending approval, approved, published, updated, resolved,
withdrawn and rejected. Old approved copy stays public until a separately approved
replacement/withdrawal is applied. Source revision changes invalidate an unpublished
approval. Publication and approval never silently follow an internal incident change.

Public access is disabled by default. Enabling it requires explicit administrator
review of the baseline statement. An empty public feed is not inferred live network
health: the baseline is an approved communication. Overall status is derived only
from that baseline and approved current announcements, with disruptions taking
precedence. Pending internal incidents are intentionally not exposed. Last update
means last approved baseline/publication, not last monitoring poll. A stale-update
notice is shown after24h; this does not guarantee incident detection/publication latency.

### Customer impact and SMS

Reuse the native Powercode inventory/mapping and NOC96 recipient engine. Native
scope selection distinguishes site/device/sector/link. NOC104 circuit/path analysis
can override legacy tower assumptions: verified functioning alternate paths exclude
a service; unverified paths, stale mappings and estimated impact remain ineligible.
Unified topology modeling alone is not observed customer-failure confirmation.
Missing/unmapped source components remain uncertain, not blanket tower outages.

Preview reports affected classifications, eligible contacts and exclusions. Existing
rules enforce active services, fresh mapping/account data, valid E.164 numbers,
recorded consent/timestamps, SMS preference, opt-out/suppression records, shared
number suppression, multiple-service deduplication, incident age, flapping,
maintenance suppression, quiet hours, rolling limits and budgets. Limits fail closed;
the native pipeline does not silently truncate a campaign. Confirmed dependency
impact is not a live test of an end-user connection.

Drafts use canonical `NotificationPlan` records. Administrator approval fingerprints
source, topology/impact, policy, template, consent and contact state. The same checks
run again at delivery; native approval APIs cannot bypass NOC109 administrator and
recovery requirements. Repeated lifecycle events reuse existing native dedupe keys.
If an already-approved legacy transition exists, review that plan rather than
creating a duplicate in the new workflow. Update events require an explicit update
number. Restoration is a separate draft and approval, targeted only to recipients
with a recorded prior notice.

Four requested operational template defaults can be initialized explicitly without
overwriting existing operator edits. The existing NOC96 template editor remains
authoritative. Templates include brand/support/opt-out placeholders. Maintenance
uses the actual recorded window in the configured timezone. There are no promotional
messages or automatic invented dates, customer approvals or pricing commitments.

### Delivery reliability

Only existing mock providers are allowed. External SMS/email/Slack transmission is
unavailable and disabled; this milestone does not claim provider compatibility.
Approved messages enter the existing durable queue. Attempts/receipts, bounded
exponential retries, opt-out rechecks, quiet-hour deferral, cancellation and audit
history remain in NOC96. The communications dashboard displays outcomes and failure
codes; old redacted plans remain readable without restoring erased recipient data.

For NOC109 plans, timeout/invalid-response ambiguity is dead-lettered for manual
reconciliation, never automatically retried. The same provider key is retained.
A real adapter must implement validated idempotency and receipt/status reconciliation
before production enablement. Mock delivery is not proof of exactly-once real SMS.
Unexpected external-process failure also needs that provider contract; no live
transport is introduced here. Completed attempts are not undone by cancellation;
only queued/retry rows are suppressed. Cancellation shares the native queue lock;
a busy worker returns a retryable conflict before any cancellation is committed.

### Maintenance and restoration

Existing NOC96 maintenance sources provide scoped targets and recorded windows.
Link canonical NOC101 work orders and NOC102 schedules when their explicit site
matches; this creates no second scheduling engine. Mark service-affecting maintenance
explicitly. Non-interrupting maintenance cannot create customer SMS. Future scheduled
maintenance can be announced without declaring an outage; start/end and completion
updates are independently approved. Operator changes to the source window require
new review. No automatic dispatch or external reminder occurs.

Restoration assessments use stored native monitor checks for documented devices,
with a configurable stability window (default300s), minimum samples (default3),
maximum inter-sample gap/freshness (default120s), no down/unknown samples in the
window, and no active warning/critical monitoring alerts. The canonical source must
already be ended through the existing incident/maintenance workflow. Unknown device
scope, missing checks, stale/future evidence or gaps do not verify recovery.

Assessments are immutable, source/policy-bound and fresh for at most300s. Approval,
publication and delivery recheck current stability. If a restoration queue waits
past freshness (including quiet hours), it is held/suppressed and needs fresh review;
recovery is not assumed. Ended non-interrupting maintenance may publish completion
without claiming recovery of an interrupted service. These checks are bounded
(max100 devices and2000 checks) and are not optical continuity, end-user or physical
power-loss proof. Native incident closure remains a separate authorized action.

## WordPress and public frontend

Target website page: `https://nwohiobb.com/network-status/`. No live website was
modified. Build the independent public-only assets:

```sh
cd frontend
npm ci
npm run build:status
```

Deploy **only `dist-status/`** under a reviewed public static path. Never publish the
private `dist/`, internal API, credentials or fixture files. The bundle imports no
NOC authentication, signup form or customer record component. It renders text via
DOM text nodes, never HTML interpolation. HTTPS and a same-origin allowlisted API
path are required; localhost HTTP is allowed only for disposable testing.

Examples: `deploy/customer-status/wordpress-shortcode.php.example` (WordPress6.5+
script modules) and `deploy/customer-status/nginx.conf.example`. The shortcode can
be maintained in a small plugin independently of the theme. Include both generated
CSS and module JS. Use `/network-status-api/v1` as the same-origin reverse proxy to
the dedicated public gateway. An independently hosted read-only page can also be
linked from WordPress. Real WordPress/theme/CSP compatibility remains unverified.

The widget refreshes every60s while visible, times out after5s, bounds responses to
512KiB, validates the versioned contract, rejects private/unapproved endpoint paths,
and shows unavailable instead of healthy after errors. It contains no customer
login, account lookup or billing form. Semantic headings, native controls and
status announcements support mobile/accessibility; no external fonts/maps are used.

API responses use ETag and `public,max-age=30,must-revalidate`. Conditional304 and
HEAD are supported. Error responses are no-store. Proxy caches may retain approved
copy for up to30s; urgent withdrawal requires an edge cache purge. Do not cache
errors as healthy. The public API paginates approved resolved history; active/current
publication count is bounded at200. Old records require explicit approved withdrawal,
not automatic deletion of history.

Rate limits:60 requests/minute per direct peer and1200 globally, including304s.
Forwarded client-IP headers are ignored by default. Counter keys are HMAC hashes
using a separate owned0600 gateway key; raw IPs are not stored. Old counters are
pruned in bounded batches after2min. Put the approved read-only API behind a short
edge cache; configure any trusted-proxy policy deliberately, not from arbitrary
client headers. Do not mistake limits per proxy peer for per end customer.

## Production isolation and credentials

Public access is preparation only, not deployment authorization. Use a **separate
process/container, environment, restricted DB identity and gateway-only rate key**.
Never give a public gateway the private NOC JWT key, app DB login, device credentials,
Powercode credentials or messaging credentials. Independent gateway-only values
satisfy shared configuration validation; there are no customer authentication routes.

The explicit helper creates `noc_status_public` using a privileged migration
connection and a generated hex password file:

```sh
cd backend
python -m app.customer_status.public_role --password-file /private/gateway-password --approve-public-gateway
```

It grants only approved-view reads and rate-counter DML, no source/customer/private
revision access. It refuses unsafe inherited grants or callable SECURITY DEFINER
functions. Password-bearing database failures are sanitized. Connection/timeout
limits are resource guardrails, not a hostile SQL sandbox. Review PostgreSQL PUBLIC
privileges and backups before activation; the helper does not silently rewrite
other applications' privileges.

`deploy/compose.customer-status.yml` is an optional internal-only profile with no
published ports, no private NOC env_file, nonroot runtime, read-only filesystem,
resource limits and dropped capabilities. Its bootstrap requires the restricted
DB user, verify-full PostgreSQL TLS, owned0600 secret files and an independent key.
Mount a trusted CA. Explicitly attach only approved DB and HTTPS proxy peers; an
internal network has no default route to arbitrary external database/equipment
hosts. Configure private DNS, firewall restrictions and trusted proxy IPs deliberately.
Compose secret files must be readable by runtime UID1000; local bind secrets do
not automatically translate host ownership. Do not pass credentials in command
arguments, public files, provisioning exports or logs.

Public gateway env: independent `SECRET_KEY`/unused shared-validator admin value,
restricted `DATABASE_URL`, `CUSTOMER_STATUS_RATE_KEY_FILE`; the provided bootstrap
loads these from private files. No NOC JWT is accepted or forwarded. Runtime device
integrations remain disabled and no public API triggers polling. HTTPS reverse
proxy, TLS/CA, role/privilege, CSP, cache purge and production provider checks remain
activation prerequisites.

## Backup, recovery and retention

Back up PostgreSQL with existing release procedures plus restricted gateway config,
independent rate key and TLS trust material in encrypted access-controlled storage.
Restore into a new isolated DB, migrate, re-grant the public role and verify the
approved projection before any public connection. Never restore over production
as an unreviewed test. All original source/customer/incident records remain canonical.

Immutable public revisions/events/recovery assessments retain communication history.
No new automatic customer/incident deletion is introduced. Native notification
redaction still removes expired contact references/content; the dashboard tolerates
redacted plans. Long-term public/audit retention requires an explicit reviewed policy.
Emergency disable: administrator disables the public policy, stop the public gateway,
revoke its DB login/restrict proxy routing and purge edge cache; independently pause
or emergency-disable the native notification queue. None of these reboots equipment.

Before28→27 rollback, stop the communications/public processes and back up their
new records. Downgrade removes only NOC109 tables/views/guards; deploy matching old
code. Native incidents, customers, outbox, topology and upstream migrations remain.
The new FK and frozen-history guards are additive; migration drift and roundtrip
checks are required before release.
